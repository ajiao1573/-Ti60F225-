# 2026-10-31 Efinity 实机联合调试

## 已执行的硬件操作

通过 Windows Computer Use 打开现有 Efinity 2026.1.132 和 Programmer。下载器检测到 FT232H（0403:6014）、Ti60F225 JTAG ID 0x10660A79，目标 1，JTAG 时钟 6 MHz。

选择 `output/segmentation_v2/Ti60_Demo.bit`，执行 JTAG 下载。Programmer 日志显示 10:02:18 开始，10:02:22 完成，10:02:23 显示 `Device is in user mode!` 和 `Programming operation completed.`。这是 JTAG 配置，未执行 SPI Flash 烧写。

UART COM16 有效应答。重配后抓帧 ID 从头计数；接受帧 2 锁定 AUY359，用户确认当时展示的图片确为 AUY359。只能据此认定这一次识别正确，不能据此认定速度、准确率问题已解决。

## 有效故障证据

- 操作前锁定 OR2972，用户确认原图为 OP2972：第二字符 P 被识别成 R。
- 随后一次重复识别返回 OF2972，用户确认对应 HDMI 真实图像仍是 OP2972：第二字符又被识别成 F。
- 原始串口状态也反复出现拒绝原因 3（非六字符）。仅凭状态不能确定是候选区域错误、光照失焦、字符掩码缺笔画还是模板比较造成。

## 测试有效性说明

1. `live_op2972_baseline.json` 的前六次试验，用户随后明确说明当时没有放车牌。这些只能作为无牌场景观察，不计入车牌拒识率。
2. `live_op2972_present_before_jtag.json` 位于放置图片、切换图片阶段，无法作为严格控制的下载前基线。
3. `live_auy359_jtag_v2.json` 开始时用户确认 AUY359，但测试期间 HDMI 实际图像已为 OP2972。文件标记为混合场景，不计算 AUY359 准确率，也不据此比较下载前后的改进。
4. 测量时间是上位机发送重识别到读回锁定状态的墙钟时间，受 5 Hz 轮询、串口、100 ms 板端快照及 USB 延迟影响，不等于 FPGA OCR 的纯计算时间。

## 下一步需要的数据

先取得 HDMI 中完整车牌及 P 字符的清晰图像，固定同一输入后再进行少量重复识别。进一步应增加只读 ROI/字符掩码和匹配分数导出，以判断笔画损失或模板混淆。未取得这些证据前不降低 OCR 门槛，也不为特定号码写死 P/R/F 替换。
