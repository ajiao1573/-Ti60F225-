# 2026-10-30 实机识别排查及上位机修复

## 实机证据

本机服务 `127.0.0.1:8765`，板端 COM11。开始排查时串口有效应答、相机输入和处理均为 30 fps，CRC 错误为 0。板端没有有效 OCR 结果，拒绝原因 3（未分出六个字符），字符数多为 0～1，失败抓帧框反复位于左上区域。

字符 ADJ 实际为 83（偏移 −45），恢复到 128（偏移 0）。短时逐项尝试边缘阈值 45/70/100/150/200，未得到有效号码，随后恢复为 27。用户使用手机显示新西兰车牌图片，开始时占画面约 80%；按提示调整尺寸、位置后继续观察。

重启新版上位机并重新连接 COM11 后，抓帧 495282 返回 `OP2972`：状态 5、字符数 6、OCR 有效、冻结、定位框有效、拒绝原因 0。处理坐标框为 x=88、y=204、w=648、h=244。相机输入 30 fps、处理 0 fps（识别锁定后正常停止接收新帧）。原始状态保存在 `tests/generated/live_after_host_fix.json`。

用户已核对手机原图，确认识别号码 `OP2972` 一致。本次实机验证覆盖手机图片输入、板端定位/分割/OCR、冻结、串口状态及上位机结果解析。该单次成功不代表任意手机图片都能识别，也不将上位机修改解释为 FPGA 定位算法已改进。

## 修改

- 结果区直接显示定位、分割、OCR 拒绝阶段、字符数量和最近抓帧编号，避免所有失败都只显示“等待识别”。
- 当前没有定位框时，单独标注最近抓帧框为历史诊断，便于判断有没有抓到真正车牌。
- 添加恢复默认参数按钮：边缘阈值 27、字符偏移 0。分步等待读回，避免连续命令撞上跨时钟控制邮箱忙状态。
- 修复参数 ACK 后首次读回尚未应用，后续虽已生效但命令状态一直显示未应用的问题。每次有效轮询都会重新核对实际参数。
- 重新打包 `host/dist/Ti60PlateControl.exe`；旧 EXE 备份到 `host/backup_before_fix/`。`build_exe.py --dist-dir` 支持在旧 EXE 运行时生成旁路构建。

未改动 RTL、OCR 模板、置信度门槛或位流。

## 使用建议
